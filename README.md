# Personal Spotify Recommender

This project started as a notebook (see notebooks/) for exploring my own saved songs — examining what my listening taste actually looks like, whether I tend to listen more to acoustic or pop music, and how those patterns have changed over time. It eventually grew into a small item-to-item and taste-cluster recommendation engine, and I wanted to take it a step further by turning it into something closer to a real service rather than a notebook that needs to be re-run from top to bottom for every recommendation.

This repo is the result. The underlying logic remains the same as in the notebook, but it is split into two parts:

- **An offline job** (`scripts/refresh.py`) that performs the computationally intensive work once — cleans your saved songs, groups them into taste clusters, builds the similarity models, and scores an entire public song catalogue (has ~900k tracks) against your taste.
- **A small FastAPI app** (`app/`) that only reads the results of that offline job. It does not access the raw data or retrain any models while handling requests, keeping response times fast regardless of the size of the public catalogue.

The project is designed for a single user (me, running it against my own library), rather than as a multi-user service. If you want to run it against your own saved songs, everything below should work as-is — see "Where the data comes from" for how data/merged_cleaned.csv and data/tracks.csv are created.

## What it actually does

Two kinds of recommendations:

- **`/recommend`** — "songs like this song," but only searches within your own library. Give it a song you already have, and it returns similar songs from the same library using cosine similarity, KNN, or a hybrid of audio features + genres + key/mode.
- **`/recommend/personalized`** — new songs you *don't* have yet, pulled from the public catalogue and ranked by how well they match your overall taste (audio features + genre overlap), optionally filtered by which of your taste clusters they are closest to.

There's also `/health`, which just confirms the API loaded its data correctly.

## Where the data comes from

Obtaining the necessary data was one of the main challenges of the project. Spotify shut down the `/audio-features` and `/audio-analysis` endpoints on **Nov 27, 2024** for any app without pre-existing extended access ([source](https://community.spotify.com/t5/Spotify-for-Developers/Access-to-deprecated-Audio-Features-endpoint-for-personal/td-p/7419715)) — so there is no longer an official way to directly retrieve information such as a track's danceability from Spotify.

To work around this limitation, the pipeline consists of three steps:

1. **`scripts/export_liked_songs.py`** — logs into your Spotify account and exports your saved songs' metadata (name, artist, genres, popularity, release date, etc.) to `data/liked_songs.csv`. No audio features are included because Spotify no longer provides them to new apps.
2. **`data/tracks.csv`** — a public dataset collected before the shutdown that includes audio features. It is not included in this repo (931 MB), but is freely downloadable — see the citation below.
3. **`scripts/merge_with_public_catalogue.py`** — merges your liked songs with the public dataset by `track_id`, keeping only the songs that appear in **both**. For me that was 523 out of ~1,900 eligible liked songs. The result is `data/merged_cleaned.csv`, which is what `scripts/refresh.py` actually uses.

So the "523 songs" referenced elsewhere is not my entire library — it represents only the overlap between the songs I've saved and the songs included in the public dataset.

## How it's organized

```
personal-spotify-recommender/
├── app/
│   ├── main.py                          # the FastAPI app itself
│   └── recommender.py                   # the SpotifyRecommender class, moved out of the notebook
├── scripts/
│   ├── export_liked_songs.py            # step 1: export your saved songs' metadata from Spotify
│   ├── merge_with_public_catalogue.py   # step 2: attach audio features via the public dataset
│   └── refresh.py                       # step 3: the offline job — run whenever your data changes
├── notebooks/
│   └── My_Spotify_Recommendation_System.ipynb   # the original exploration notebook
├── data/                  # tracks.csv and liked_songs.csv go here (not committed)
│   ├── README.md
│   └── merged_cleaned.csv           # committed — small enough, and saves the next person a step
├── artifacts/             # generated by refresh.py, committed for deploys
├── Dockerfile
├── requirements.txt
└── .env.example
```

The split between `app/` and `scripts/` is the whole point of this design: everything in `scripts/` is allowed to be slow and is run by hand whenever you want. `app/` is not allowed to be slow, because someone (you, or whoever you send the link to) is waiting on it.

## Running it locally

```bash
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env

# edit CLIENT_ID / CLIENT_SECRET near the top of scripts/export_liked_songs.py
# (get these from https://developer.spotify.com/dashboard), then:
python -m scripts.export_liked_songs           # -> data/liked_songs.csv
# put the public dataset at data/tracks.csv, then:
python -m scripts.merge_with_public_catalogue  # -> data/merged_cleaned.csv
python -m scripts.refresh                       # -> artifacts/

uvicorn app.main:app --reload
```

Open `http://127.0.0.1:8000/docs` and try it out. Every time you add new liked songs, rerun the pipeline from `export_liked_songs` (or just `merge_with_public_catalogue` + `refresh` if you already have a recent `liked_songs.csv`) and restart the API.

## Running it in Docker

This simulates an actual deployment — using the same image and environment whether it is running on your laptop or on a server.

```bash
python -m scripts.refresh     # make sure artifacts/ is up to date first
docker build -t personal-spotify-recommender .
docker run -p 8000:8000 personal-spotify-recommender
```

`docker run -p 8000:8000` only exposes the API on your own machine (`http://127.0.0.1:8000`) — it is not accessible to others from that alone.

## Deploying it somewhere public

I used [Render](https://render.com) which deploys directly from a Dockerfile. The main limitation is that it goes to sleep after 15 minutes of inactivity and takes 30–60 seconds to wake up on the next request. This is reasonable for a personal project, but less suitable for an application that requires consistently low response times.

1. Make sure `artifacts/` is current (`python -m scripts.refresh`) and pushed to GitHub. **Keep the repo private** — `artifacts/` is derived from your personal listening data.
2. On Render: New → Web Service → connect the repo → it should auto-detect the Dockerfile → pick the Free instance type → deploy.
3. Render gives you a public URL. Send that instead of `127.0.0.1`.

**Live at:** https://my-spotify-recommendation-system.onrender.com/docs (first request after a while may take 30-60s while the free instance wakes up)

Redeploy (rebuild + push) any time you rerun the refresh script.

## Things worth knowing before you rely on this
- **`/recommend` only searches your own library.** If you request a song that isn't in your saved songs, you'll get a 404, even if that song exists in the public catalogue. It is a different type of search (a fixed similarity matrix built once for your library only), rather than a search that supports arbitrary songs.
- **This is single-user by design.** There is no auth, no per-user data, and no database — just your library, your artifacts, and your API. Supporting more than one person would require a substantially different architecture.
- **`scripts/export_liked_songs.py` has your Spotify `CLIENT_ID`/`CLIENT_SECRET` as constants near the top**, not in `.env`. DO NOT make the repo public without replacing them with placeholders first.
